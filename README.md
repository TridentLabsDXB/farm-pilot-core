# FARM-PILOT CORE

Single-customer, fully offline appliance edition of Farm-Pilot. One Node process: embedded MQTT broker (Aedes, loopback only), SQLite (WAL), REST + WebSocket API and the SCADA View SPA. No Docker, Node-RED, InfluxDB, MinIO or Postgres. **Control never depends on this PC: the PLC keeps its own logic.** This repo is Milestone 0 + 1 + 2 (test bench; Milestone 2 = C1 LoRa gateway over Modbus, T/H sensors).

## Run
Bench (core.farm-pilot.com host, as root):
```bash
./deploy.sh            # git pull, npm ci, build, restart, health check
systemctl status farmpilot-core
journalctl -u farmpilot-core -f
```
Layout on the bench: code + `node/` (Node 22 tarball, SHA256-verified, gitignored) in `/opt/farmpilot-core`; data in `/var/lib/farmpilot-core/core.db`; settings in `/etc/farmpilot-core.env` (see `deploy/farmpilot-core.env.example`); unit `deploy/farmpilot-core.service` (User `fpcore`, `MemoryHigh=1500M`, `MemoryMax=2G`, `CPUQuota=200%`, `CPUWeight=20`, `IOWeight=20`). First boot creates user `admin`; the random password is in `/var/lib/farmpilot-core/initial-admin-password` (mode 600; or set `CORE_ADMIN_PASSWORD`). Delete the file after the first login.

Local dev: `npm i && npm --prefix web i && npm run build && HOST_BIND_IP=127.0.0.1 DB_PATH=./dev.db DATA_DIR=. npm start`.

Environment: `HOST_BIND_IP` (default 127.0.0.1), `PORT` (4100), `MQTT_PORT` (1884, loopback only), `DB_PATH`, `COOKIE_SECURE` (`auto` | `true` | `false`), `RETENTION_DAYS` (30), `COMMAND_TIMEOUT_SEC` (10, Admin can change), `COMMAND_DEDUPE_MS` (3000).
`COOKIE_SECURE=auto` marks the session cookie Secure only when the request came over HTTPS (X-Forwarded-Proto from NPM). On the real box the hotspot serves plain HTTP, so use `auto` or `false` there.

## Simulator (dev / bench only, never on the box image)
`deploy/install-sim.sh` installs `farmpilot-core-sim.service`; `deploy.sh` never does. It publishes Unified payloads every 5 s and echoes pump commands. `SIM_NO_ACK=1` makes it stay silent (tests the timeout state); it ignores commands older than 15 s.

## MQTT topics (farm slug `demo-farm`)
| Topic | Direction | Payload |
|---|---|---|
| `farmpilot/demo-farm/air` `/soil` `/water` | device -> runtime | Unified: `{"ts":iso,"sensors":[{"key":"AIR1","type":"temp_humidity","readings":{"temp":24.1,"humidity":55}}]}`; the pump status is sensor `WPump1`, reading `status` 1/0, in `water` |
| `farmpilot/demo-farm/cmd/pump1` | runtime -> device | `{"cmd_id","action":"on"\|"off","ts","by"}` QoS 1, **not retained** |
| `farmpilot/demo-farm/ack/pump1` | device -> runtime | `{"cmd_id","ok":true,"state":"on"}` |

Command states: `sent` -> `confirmed` (ack) or `timeout`. On start-up any `sent` command is closed as `timeout` and **never re-published**. A repeated same-pump same-action command within 3 s is ignored (double tap). The broker sits behind the `MqttBroker` interface (`src/broker.ts`); the runtime talks to it as a normal MQTT client, so Mosquitto can replace Aedes.

## Schema (SQLite, `auto_vacuum=INCREMENTAL`, WAL)
`series(id,topic,sensor_key,metric)` · `latest(series_id,value,ts)` · `history_raw(series_id,ts,value)` WITHOUT ROWID, 30 days · `rollup_hourly(series_id,hour_ts,avg,min,max,n)` kept · `users(role operator|admin)` · `sessions(token_hash,...)` · `settings` · `commands(id,pump,action,status,username,role,created_at,resolved_at,note)` · `audit_log(ts,username,role,action,detail)` append-only (triggers refuse UPDATE/DELETE).
Jobs: rollup every 10 min (idempotent); retention at start + every 6 h in 5000-row batches with WAL checkpoints and `incremental_vacuum`; command sweeper every 1 s.

## API
`POST /api/login|logout`, `GET /api/me|state|health`, `POST /api/commands`, Admin: `GET/POST /api/users`, `POST /api/users/:id`, `PUT /api/settings`. WebSocket `/ws` pushes `telemetry` and `command` events. Roles: Operator = view + commands; Admin = also Settings.

## Firewall (test bench)
No public port is opened. The runtime binds the private cluster address (`10.0.0.3:4100`) and the broker binds `127.0.0.1:1884` only. ufw's default INPUT policy is DROP.
Rule added 2026-11-15: `ufw allow from 172.16.0.0/12 to any port 4100 proto tcp comment 'NPM container -> farmpilot-core'`.
Reason: the shared Nginx Proxy Manager runs as a Docker container on this host and reaches the runtime from a Docker network (observed source `172.19.0.3`). Without the rule ufw dropped those packets (`[UFW BLOCK] ... DPT=4100`) and NPM answered 504. The existing rules already allow that range to ports 3000, 10000 and 8086 the same way. Access is restricted for users by the NPM Access List (VPN address range), not by this rule.

## Milestone 2: C1 gateway (ThingSend XZ-DS-MUS2, Modbus RTU, T/H sensors)
Source of truth: manual "XZ-DS-MUS2 manual V20". Everything the manual does not say is marked `ASSUMED` in `config/gateway-thingsend.yaml` and must be verified on real hardware.

**Enable polling** (off by default; without `GW_TRANSPORT` the runtime behaves as in Milestone 1) in `/etc/farmpilot-core.env`:
`GW_TRANSPORT=tcp|rtu-tcp|rtu-serial`, `GW_HOST`/`GW_PORT` (tcp, rtu-tcp), `GW_SERIAL_PATH` (default `/dev/ttyUSB0`), `GW_BAUD` (9600), `GW_PARITY` (none), `GW_ADDRESS` (0 = map default), `GW_TIMEOUT_MS` (1500), `GW_RETRIES` (2), `GW_REGMAP` (`config/gateway-thingsend.yaml`). On the real box use `rtu-serial` (RS485 / USB-RS485, 9600 8N1); `serialport` is an optional dependency loaded only then. If the register map is invalid the gateway part is disabled with a clear log line; the rest of the runtime keeps running.

**Code map:** `src/drivers/modbus/` (frames, transports, priority-queue master, register-map loader, driver) · `src/gateway/` (logic = planner, calibration, staleness, health; registry; service = poll loop + Send to Gateway; routes; health view) · `src/tools/gateway-sim/` (simulator; dev only) · `config/gateway-thingsend.yaml` (register map, types as config blocks; gas, light, door_smoke, soil are disabled placeholders for Milestone 2b).

**Gateway simulator** (`farmpilot-gateway-sim.service`, bench only, installed by `deploy/install-gateway-sim.sh`): Modbus TCP on 127.0.0.1:5020, RTU-over-TCP on 5021, control HTTP on 127.0.0.1:5030. Eight physical T/H sensors (serials `112600310`..`112600317`) only transmit once a group with their serial is configured. Unconfigured groups read 0xFFFF like the real gateway. `SIM_TIMESCALE=60` makes a 5 min interval transmit every 5 s (bench speed-up; CORE's own timing stays real). Control: `POST /freeze?serial=`, `/unfreeze`, `/zero?serial=` (registers read zeros), `/voltage?serial=&v=3.0`, `/stop` and `/start` (gateway stops answering), `/reject?on=1[&serial=]` (writes rejected), `/preconfig?type=th&slot=1&serial=&interval=` (interval in minutes; a group configured "with the maker's tool"; slots are 1-based like everywhere else), `/replay` (POST JSON `{"loop":false,"frames":[{"t":0,"type":"th","slot":1,"regs":[235,580,360,65456]}]}`), `GET /state`. Optional virtual serial pair with `socat` is described at the top of `src/tools/gateway-sim/main.ts`.

**Behaviour decisions**
- **Reporting intervals are in the gateway's unit, per sensor** (T/H: whole minutes 5..240, default 5; presets 5, 10, 15, 30 plus a custom value; 30 s and 1 min do not exist). Enforced by the API (HTTP 400), the range comes from the register map (`interval.unit/min/max`). The database, the API and Send to Gateway all use the native unit (minutes); the view also carries `intervalSec` for timing. A value that is already stored outside the rule (adopted from the gateway, an old backup) stays displayable and is flagged NOT ALLOWED until changed. The commissioning-mode mechanism is kept but only shows for a type that lists `commissioning_presets` (none today).
- **Operators get an allow-list, not a filtered admin view** (`buildView` in `src/gateway/health.ts`): label (never the serial: an unlabelled sensor is "Sensor N"), values, state words, battery level and low flag, signal band, last-change time. No serial, slot, raw value, calibration data, interval, threshold, setting or audit row; alarm objects carry no serial. `/api/state` serves only `farmpilot/*` MQTT topics (the gateway series, keyed by serial and holding raw values, never). Every other route answers an Operator with 403. `test/operator-access.test.ts` boots the real app, calls EVERY registered route as an Operator, scans every response and every WebSocket message for serials, `*_raw`, forbidden keys and raw numbers, and fails if anything leaks.
- **Alarm freeze:** while the gateway is offline, sensor alarms are neither raised nor cleared; open ones stay open and show STATUS UNKNOWN (GATEWAY OFFLINE). A cleared alarm records `clear_reason` (`recovered`, `sensor_removed`, `other`); NO UPDATE also records `last_data_at`, the time the sensor's data last changed.
- **Pump commands ask first:** START and STOP open a one-step confirmation ("Start Pump 1?") for everyone, so a stray touch cannot send a command. Delete user also ends that user's sessions and refuses to remove yourself or the last active Admin.
- **Migration rehearsal:** `node --import tsx scripts/rehearse-migration.ts <copy.db>` migrates a COPY and compares row counts, slots and integrity. Run it on a backup copy before a deploy that changes the schema.
- **Commissioning mode** (only for a type with `commissioning_presets`; none in map v2) switches itself off after 8 hours (audited as `gateway.commissioning.auto_off`, user `system`).
- **Alarm history:** table `alarm_events` (kind, source, severity, text, raised_at, cleared_at, acknowledged by/at), written by `AlarmTracker` (`src/gateway/alarms.ts`) after every gateway report and every 15 s; one row per alarm episode. The Alarms page shows active alarms with an Acknowledge button and the recent history. `raised_at` is when CORE detected the alarm, not when the sensor stopped. Operators see no serials in the history API.
- **Delete all sensors in gateway** needs the farm name typed exactly (checked by the API, not only the UI). A wrong text is refused and audited (`gateway.delete_all.refused`); a real run writes `gateway.delete_all.request` before the write and `gateway.delete_all` (or `.failed`) after it.
- **Build stamp:** `deploy.sh` writes `dist/BUILD` (short commit, `-dirty` if uncommitted changes were built); `/api/health` returns it as `build`.
- **Slots are numbered 1..N** (T/H 1..30) in the database, the API, the UI, the simulator and the backup file (backup format version 3: decimal serials, intervals in minutes; older backup files are refused with a clear message). Only the Modbus address calculation subtracts one: register = `config.base + (slot - 1) * regs_per_group`. A one-time migration (`settings.slots_1based`) converted databases written by the first Milestone 2 build. Old `audit_log` rows from before 2026-11-16 still show the 0-based number in their de
- **Bench findings of 2026-11-16 (map v2):** gateway address 7, PID 300; serial = plain decimal of the u32 (`06 b6 24 fd` = 112600317, fewer digits allowed), word order high first; group = `[serial_hi, serial_lo, ST, CMD]`; ST = interval, probably minutes (5 on all bench sensors); unconfigured config slots read 0xFFFF (so 0xFFFF = empty; zeros are also treated as empty until the read-back after a clear is checked); a configured sensor that never transmitted reads all zeros = NO DATA; FC03 data / FC04 config split confirmed; a 120-register read takes about 0.29 s at 9600. A one-time migration (`settings.serial_decimal_minutes`) converted databases from the hex/seconds build (serials, history series keys, calibrations, points, intervals clamped to 5 min minimum; everything shows NOT SENT until the next read-back / Send).tail text (the log is append-only).
- The gateway is the truth for "sent": `sent_slot`/`sent_interval` mirror the last config read-back (FC04). IN GATEWAY / CHANGED / NOT SENT derive from them.
- Send to Gateway (per type): pause polling, read back groups, plan (changed groups only, zeros for removed), ask for confirmation if anything is removed, moved or replaced, write with FC16, read back and verify every group, retry once, resume polling in `finally`. Groups in the gateway that CORE does not know are never touched and never auto-added: they show as NEW SENSOR FOUND (ADD / IGNORE) and their slots are reserved.
- A sensor deleted in CORE (or replaced) is cleared in the gateway only by the next confirmed Send; its slot is not reused before that.
- History: topic `gateway/<type>`, key = serial, metrics `temperature`/`humidity` (calibrated) and `temperature_raw`/`humidity_raw`, `voltage`, `rssi`; written only when the channel frame changed. Rollups, alarms and the SCADA View use the calibrated series.
- Staleness: fingerprint of the whole channel frame; identical for 3 intervals of that sensor = NO UPDATE (all zeros = NO DATA). Heuristic until validated on hardware.
- Poll period: the configured default (30 s) but never longer than half the shortest sensor interval in use, floor 10 s; backoff while failing; gateway OFFLINE after 3 failed cycles (a Modbus exception reply does not count: the gateway answered).
- `serialport` and `yaml` were added as dependencies. The UI follows `core-ui-spec-direction-a.md` (light default, dark toggle, `web/src/tokens.css`); the old demo AIR/SOIL/WATER MQTT cards were replaced by structure-built zone cards, the pump card is unchanged in behaviour.

**ASSUMED (verify on hardware, then edit the YAML):** gateway address 7 as a general default (it is the test unit's); interval unit minutes and range 5..240 (MDMS manual row + bench value 5; confirm by watching the real update rate) and the soil/gas/light/door ranges; control (CMD) values other than 0; version register value; what a config slot reads after writing zeros; low-voltage 3.20 V and the battery icon bounds (empty = threshold minus 0.4 V, full = 3.60 V; bench sensors read 3.77 to 3.83 V; battery type not confirmed); RSSI good above -90 / poor below -105 (bench -40 dBm is not representative).
**How to swap in real values:** edit `config/gateway-thingsend.yaml` (bump `map_version`) and restart `farmpilot-core`; no code change. A new sensor type = a config block with `enabled: true`.

**Farm Profile and Settings menu (change request 2026-11-16, UI spec direction A).** Settings (Admin only) has six items in this order: Farm Profile, Farm Structure, Sensors Gateway, Sensors, Users, Backup (`#/settings/<farm-profile|farm-structure|sensors-gateway|sensors|users|backup>`; old `gateway` / `structure` paths redirect; phone shows a list of six rows with a back arrow; side-nav badges show OFFLINE / SYNC FAILED, n NOT SENT, backup OLD, profile SET UP). Operators are redirected to SCADA and get 403 on every settings route.
- **Data:** tables `farm_profile` (one row) and `farm_contacts`. API: `GET /api/farm-profile/public` (any user), `GET/PUT /api/farm-profile`, `POST/DELETE /api/farm-profile/logo` (raw PNG/SVG body, 256 KB, magic bytes checked, SVG with scripts/external refs refused, served as an image with a sandbox CSP), `GET/POST/PUT/DELETE /api/farm-contacts`, `GET /api/farm-contacts/alarm-view` (name, role, phone only). PUT validates per field (400 with `fields`), rejects unknown fields; every write is audited with old and new values (logo: hash only). Code: `src/gateway/profile.ts`, `profile-routes.ts`, `thresholds.ts`; page `web/src/FarmProfilePage.tsx`.
- **Thresholds:** register-map default < Farm Profile value (NULL = default), read on every call, so changes apply without a restart: low-voltage per type, RSSI good/weak, `stale_multiplier` (NO UPDATE) and `offline_multiplier`, calibration due days. The old Gateway-page fields for these were removed (`PUT /api/gateway/settings` refuses them). Timezone, date/time format and temperature unit are display only (storage UTC, degC); the sensor detail and calibration wizard stay in degC.
- **One Send to Gateway job:** `web/src/Sync.tsx` (`useSync`) is used by Sensors Gateway (full: gateway card with address and PID, slot usage, WILL BE SENT, RESULT, NEW SENSOR FOUND, danger zone) and Sensors (top bar with the same button).
- **Set gateway address** (`POST /api/gateway/set-address`, farm name typed, never 123 or 160, written to the CURRENT address, never broadcast, audited): after it, set `GW_ADDRESS` in `/etc/farmpilot-core.env` too.
- **Backup** also carries the profile (with logo) and contacts; an import is validated first, and after a restore the Admin must confirm the time zone (banner on Farm Profile).
- **ASSUMED:** RSSI -90 / -105, due-days default (none), backup warning after 7 days (`backup.warn_days`). CORE sends no SMS/email/push; contacts are stored and shown only.

**Hardware validation checklist (industrial PC, real gateway over RS485).** Already confirmed on the bench capture of 2026-11-16: gateway address and PID registers, FC03 data / FC04 config split, group register order, serial word order and decimal mapping, 0xFFFF for empty config slots, all-zero data for a never-received sensor, 0.29 s per 120-register read. **Still to verify:** version register (0x0002); interval unit (minutes) and range, by observing the real update rate after changing it; control register meaning; value of a config slot after writing zeros; behaviour of the data registers for a **silent sensor that was reporting** (remove a working sensor's battery, press Read every few minutes for at least 3 intervals and record the 4 data registers: frozen, zeros or other; also record voltage/RSSI variation of a healthy sensor over several reports; then adjust `FingerprintDetector` and the simulator's freeze mode); persistence of groups after a power cycle; whether groups written by CORE behave the same as with the manufacturer's tool; soil data start (0x4001 vs 0x5001) before Milestone 2b; battery type and voltage against remaining life (low-voltage threshold, icon bounds in `web/src/ui.tsx` `Battery`).

**Slot mapping:** slots are 1..N; `test/slot-address.test.ts` proves slot 1 = first group (T/H config 0x0100, data 0x0001), slot 30 = config 0x0174 / data 0x0075, every type's last slot, the bytes on the wire, and that slot 0 / 31 are refused before any request is sent.

**Tests:** `npm test` (unit: register map, decoding, planner, calibration, staleness, rate limit; integration against the simulator over TCP and RTU framing). `scripts/acceptance.mjs` runs the acceptance against a running core + simulator. By default it refuses anything but an isolated dev instance (loopback, port other than 4100); the bench needs `--bench`. It creates its own admin user `acceptance` (random password) with the credentials in `USER_NAME`/`PASS`, acts as that user, and deletes it at the end, also after a failure or Ctrl-C. `DELETE /api/users/:id` (Admin, never yourself) exists for that and is audited; the audit log keeps the user's rows.
